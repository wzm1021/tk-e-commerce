# TK 到 1688 货源匹配

用户只需提供 TK 商品链接或选品结果，不要求预先知道 1688 链接。目标是建立有依据的候选货源与销售规格映射，并把确认后的采购条件交给利润测算。

## 当前运行模式

- **已可用**：批量任务整理、候选文件导入、规格冲突检查、人工待办与利润测算交接。
- **待接入**：1688 实时图搜、词搜和详情客户端。用户已提供图搜 `product.search.imageQueryBasic`、详情 `alibaba.cross.productInfo` 的官方文档链接；请求字段、签名、权限、货盘范围、收费及响应字段仍待文档内容与授权验证。
- 运行 `scripts/prepare_batch.mjs` 只处理本地文件，不联网、不读取 key，不代表已经搜索 1688。

## 读取路径

- TK 信息提取与 1688 接入：读[数据接入](references/data-sources.md)。FastMoss 数据沿用[共用证据规范](../../docs/fastmoss-analysis-contract.md)；1688 是本 skill 明确新增的供应链来源，不用其价格替换 TK 指标。
- 货源比对：读[匹配方法](references/methodology.md)。
- 批量文件、状态及交接：读[数据与交付格式](references/report-contract.md)。
- 输入可从 [batch-template.json](assets/batch-template.json) 开始；[batch-example.json](assets/batch-example.json) 仅为虚构的无 key 演示。

## 工作流

1. 接收 TK 链接清单，保留原链接、市场、商品及可得 SKU ID。短链接/身份不清时先解析，不从标题猜商品 ID。
2. 获取主图、标题和关键规格，确定用户实际要卖的单元：单件、套装、容量、材质、适配及配件。可先找货，但目标规格未确认时不能完成货源确认。
3. 经已授权通道取候选；每商品默认先用 1 张清晰主图、必要时补 1 张图与中文关键词，初取约 10 个候选，只深查 3 个。实际参数和额度按供应商文档执行。
4. 用图片找候选，再以商品详情和 SKU 规格排除冲突。相似度只用于排序，不能当成同款证明。
5. 分别保存候选状态、实测状态和报价状态；人工确认的具体 offer/SKU、采购数量和销售单位换算才能用于确认后的成本。
6. 为候选创建初筛利润方案；输出待询价、待确认、待买样、待测量任务。没有货源数据时照常交付任务清单与缺口。

## 本地命令

在项目根目录运行：

```sh
npm run sourcing:prepare -- skills/tiktok-supplier-matching/assets/batch-example.json
```

结果为 JSON，含每个商品的搜索计划、候选、状态和人工任务。持久文件写入新的 `output/<任务名>-<日期>/` 目录，保留原始文件，不覆盖人工确认记录。

## 关键边界

- ID 始终为字符串；映射粒度至少为市场 + TK 商品/目标规格 + 1688 offer/SKU。不同套装、卖家和变体不能合并。
- 未接入、接口错误与搜索未命中分别记录；不把权限错误当作“无货源”。
- 同图商品不能认定是 TK 卖家的原供应商、原厂或相同质量；样品与文件验证也不能证明原供应关系。
- 采购、联系商家及下单不由本 skill 自动执行。用户明确要求后再使用具备相应权限的通道。
